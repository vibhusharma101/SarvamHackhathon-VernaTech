### MAJOR

- `api/sql/schema.sql:63-72` vs `api/app/routers/scoring.py:64-77` — the schema defines `criterion_score`
  specifically to hold the 3 individual per-run scores (`run_index 1..3`) as an audit trail, but nothing in
  the codebase ever writes to it. `scoring.py` aggregates the 3 LLM runs in memory and writes only the
  aggregated `criterion_result` row. The raw per-run disagreement — the thing `low_consistency` is supposed
  to summarize — isn't persisted, so it can't be inspected later or replayed into `services/harness_runner.py`
  without re-calling the LLM. Given the PRD's own words ("Don't hide scorer disagreement"), losing the raw
  runs undercuts that claim on audit. Fix: insert one `criterion_score` row per run inside the loop in
  `_run_scoring_pass`, before aggregating.

- `api/app/routers/scoring.py:54-70` and `api/app/services/harness_runner.py:32-42` — criterion identity is
  matched by string equality on the LLM's echoed `"name"` field against `rubric_criterion.name`
  (`criterion_by_name.get(name)`). If the model paraphrases or truncates a criterion name in its JSON output,
  `criterion_id` silently becomes `None` on insert (the column is nullable) rather than raising — the score
  is recorded with no link back to the rubric row it's for. Given `temperature=0.1` and a fixed prompt this
  is unlikely per-run, but it's a silent-failure mode with no logging, in the one place a judge is most likely
  to interrogate ("show me how this score maps to that criterion"). Recommend either an explicit criterion
  index/id round-tripped through the prompt, or a hard failure (raise, don't insert with a null FK) when a
  returned name doesn't match.

- `api/app/routers/harness.py:43-44` — `next(r for r in batch_results if ...)` raises `StopIteration` (surfaces
  as an unhandled 500) if either session in a pair produced no matching result — e.g. one session had zero
  turns. The PRD is explicit that the harness is "never cut" and the one thing that isn't a commodity voice
  bot; a single malformed profile shouldn't be able to 500 the whole batch and silently drop every other
  pair's results too (since `run_harness_batch` processes serially but this loop has already returned before
  any partial results are saved for pairs earlier in the list — actually not true, `db.table("harness_pair").update(...)` happens per-iteration so earlier pairs ARE saved before a later `StopIteration` — but the caller still gets a 500 with no indication which pairs succeeded). Recommend catching per-pair and continuing, returning a partial-success list with a `dict` per response.

### MINOR

- `api/app/services/stats.py:16-17` — docstring says `criterion_id -> aggregated score` but every caller
  (`harness.py:46-47`) actually keys these dicts by criterion **name**, not id. Harmless today because both
  sides of the intersection use the same key space consistently, but the docstring will mislead the next
  reader into assuming id-stability that isn't there.
- `api/app/routers/scoring.py:44-48` — new `scoring_pass` is inserted as `is_current=True` and older passes
  are flipped to `False` in a second statement, so there's a brief window where two passes could both read as
  current under concurrent rescore calls on the same session. Not exploitable in this app's single-recruiter
  usage pattern; worth a comment if left as-is.
- `web/app/screen/[sessionId]/lib` mic path — `MicCapture.tsx` uses the deprecated
  `ScriptProcessorNode` (already called out in a code comment in `lib/audio.ts` as a deliberate 6-hour-window
  tradeoff). Flagging here only so it isn't forgotten post-hackathon; not a scaffold defect.
